### First pass details

- **P-01 · Important.** `docs/architecture.md` and `eslint.config.js` let `src/app/`, `src/ui/` and `src/data/` import only types from `src/domain/`. The plan exposes from `match-session-store.ts` only `grid` and `warnings`, so the grid components (T038, T041) would need `gridColumns`, `columnKey`, `cellKey` (to look up `GridWarnings.lightRedCells`), `cellState`, `playerCounter` and `isRuleWindowColumn`, and `format-picker.tsx` (T023) would need `FORMAT_IDS`. On the data side, T034 asks `loadGrid` to return the call-up "sorted", which needs `comparePlayers`, and turning the stored integer into `FormatId` needs `isFormatId`. All of these are domain functions, so ESLint `boundaries` would fail. The plan must define what state publishes for the interface (for example a grid view with columns, rows with counters, cell states and warning flags, and the format options), and move sorting and narrowing from `src/data/` to `src/state/`.
- **P-02 · Important.** T019 puts `src/data/test-database.ts`, a helper built on `better-sqlite3`, inside `src/data/`. It is not a `*.test.ts` file, so the boundaries rule for `data` (only `expo-sqlite` and `drizzle-orm`) rejects the import. This contradicts the plan's own line "`better-sqlite3` is only imported by tests", and the helper would also count in coverage. Move it to `tests/` (test category) or name it so that it falls under `TEST_FILES`.
- **P-03 · Important.** The nine plan questions were answered, but the answers live only in `plan.md`. Several of them are user-visible behaviour that the spec does not contain: "07" rejected (RF-016 says "one or two digits"), length limits of 40 and 500 and scores 0–999 (RF-013, RF-016, RF-025), the date shown as «11/11/2026», the format being editable in the new-match form, the save-failure message and its new key `error.saveFailed` (not in the approved Spanish texts table), undo skipping missing cells (RF-057), and the legend with «≠» and «!» (RF-065, RF-066). Constitution principle 12 says the answer is recorded in the spec, and the Planner role forbids adding scope that is not in the spec. Some tasks also add small behaviour of their own: T029 "draft discarded when leaving", T046 "tapping outside the dialog cancels it", T051 "change to the same format still asks". Record them through the Specifier (Clarifications, the affected RFs and the texts table) before approval.
- **P-04 · Important.** Principle 5 says children's names never leave the device. By default, iOS iCloud and computer backups include the app's data, and the plan leaves this to Security in T018 (question 6) while the constitution check marks principle 5 "Yes" and "Pending: none". Mark the row "Pending", and settle it before D2 approval, because D2 is the first delivery that stores names. Security should also check whether `android.allowBackup: false` still allows device-to-device transfer on Android 12 and later, which may need `dataExtractionRules`. If the decision adds native configuration, `docs/security.md` should record it.
- **P-05 · Important.** RF-082 says "Every change is saved on the device at once, without a save button". The approved Spanish texts include `common.save` «Guardar» "in forms", and the plan has team, player and match forms. The spec should say what RF-082 covers: grid marks and confirmed actions are saved at once, while forms are saved with «Guardar». It should also say what happens to a half-filled form when the app closes, because E-019 and the T022, T029 and T035 "Interruptions" scenarios depend on it.
- **P-06 · Important.** Plan and T016 compare `isRuleImpossible` with brute force "up to 5 players × 3 window periods". Three window periods means the 4-period format, where every window period needs 5 X and every player needs one rest. With 5 players or fewer, no filling can give 5 X per period and a rest to everyone, so the rule is always impossible and both sides always return `true`: the property proves nothing. Generate call-ups of at least 8 players (4 periods) and 9 to 12 players (6 and 8 periods), with most cells already filled, so that brute force runs only over a few empty cells. Cover all three formats, because the minimums of 2 are never exercised otherwise.

### 4. T024: the focused-test check

Pattern (`tasks.md:340`): `^[[:space:]]*((it|test|describe)(\.[A-Za-z]+)*\.(only|skip)|x(it|test|describe)|f(it|test|describe))(\.[A-Za-z]+)*[[:space:]]*[(`]`. Read against `scripts/verify.sh:46-47`, mentally tested:

| Input (at the start of a line)                  | Result   | Right?                                                      |
| ----------------------------------------------- | -------- | ----------------------------------------------------------- |
| `it("RF-079: 4 and 6 periods fit at 375 pt", …` | no match | yes: `f(it…)` needs the line to begin with `fit`            |
| a title alone on its own line, `"… fit …",`     | no match | yes: the line begins with a quote                           |
| `it.only(`                                      | match    | yes                                                         |
| `fit(`, `fdescribe(`, `ftest(`, `xit(`          | match    | yes                                                         |
| `describe.skip.each(`                           | match    | yes (`.skip` found after backtracking, `.each` by the tail) |
| `it.only.each(TABLE)(`, `test.concurrent.only(` | match    | yes                                                         |
| `it.each([...])("...")`, `it.each(TABLE)(`      | no match | yes: not focused                                            |
| `// it.only(`, `const fit =`, ` * it.only(`     | no match | yes                                                         |

No false positive or negative on the five cases requested. Remaining weaknesses, all small:

- **False negative, not at the start of a line:** `const d = process.env.CI ? describe : describe.skip;` and `if (x) it.only(...)`. The old pattern caught them. Prettier keeps normal test calls on their own line, so this only matters for conditional-skip idioms. Minor: add `describe\.skip|it\.skip|test\.skip|\.only\b` as a second, line-anywhere pattern restricted to `\.(only|skip)\b` outside quotes, or accept and document.
- **False negative with generics:** `it.only<Foo>(`: the next character must be `(` or a backtick. Rare.
- **False positive:** a helper called `fit(` at the start of a line, for example inside a multi-line `expect(\n  fit(375, 6),\n)` in the T053 tests. Plausible, because the layout file is about "fit". Avoid by naming the helper differently, and say so in T053.
- **Exit codes:** `grep` exits 2 on a missing directory; `if grep …; then` treats that as "no match", so a typo in an argument passes silently. The old script had the same `2>/dev/null`. Make the script exit 2 itself when an argument is not a directory (the T024 scenario "an empty folder → exit 0" stays true).
- **Consistency with `verify.sh` and the tests:** the same `src tests` default, the same message and `*.test.ts(x)` globs: consistent. The script needs the executable bit (`git update-index --chmod=+x`) and should `cd` to the repository root when no argument is given, as `verify.sh` does. The test must follow `tests/scripts/check-traceability.test.ts` (`spawnSync`, fixtures in a temporary folder created at run time, `IT` placeholder idea): T024's rule "quoted strings, never a template literal whose lines start with a call" is the same precaution, and it also protects the new check from flagging its own test. BSD (macOS) and GNU grep both accept this ERE; `[(`]` is fine inside single quotes.

### What happens when `setResourceValues` fails

The `catch {}` swallows both `createDirectory` and `setResourceValues` errors. Judgement: acceptable for the behaviour (the plan and constitution say the app never blocks the coach, so it must open), but not acceptable as silent. If the write fails, the folder stays included in iCloud and computer backups and nobody can tell: children's names could reach iCloud without any trace. How likely: low (the call fails on a full disk, a damaged volume or a missing folder, and a missing folder is already handled by `createDirectory`). How long: the block runs at every launch, so it heals itself on the next successful launch, and iCloud backups usually run while the device is idle and charging, so the exposure window is short but real. Safer handling inside the plan (no change to the plan, the failure is still ignored for the user): keep the `do/catch`, but in the `catch` write one fixed message with `NSLog`, for example `NSLog("with-backup-exclusion: the database folder could not be excluded from backups")`. It must not print the error, the path or any name (a path under `Documents` has no player data, but the rule is no data in logs, and a fixed text is simplest to audit). Optionally read the value back after setting it (`resourceValues(forKeys: [.isExcludedFromBackupKey])`) and use the same message if it is not `true`. A test can check that the `catch` is not empty and holds no interpolation.

Method: read the diffs and the final files; `npx expo prebuild --platform android --no-install --clean` in two temporary copies outside the repository (no `ios/` or `android/` was created in the repository), one without `APP_VARIANT` and one with `APP_VARIANT=production`; `npm audit`, OSV-Scanner, gitleaks and Semgrep as `scripts/verify.sh` runs them. No code was changed.

### T087 · message and Retry

- **No data on screen or in logs.** `DatabaseOpenFailed` (`src/ui/database-open-failed.tsx`) shows two fixed texts from `es.json` (`db.openFailed`, `db.retry`) and takes no error prop. `useDatabaseStart` (`src/state/use-database-start.ts:34-36`) drops the rejection reason (`() => finish("failed")`) and returns only `status`, `retrying` and `retry`. No `console` anywhere in `src/` (grep, and the source test). Nothing in `src/`, `plugins/` or `app.config.js` uses `fetch`, `XMLHttpRequest` or `WebSocket`.
- **Nothing is deleted or reset.** No `deleteDatabase*` in `src/`; `openAppDatabase` still opens the same name `planificador.db`, and on failure only closes its own connection (`src/data/database.ts:23-26`). The text promises "No se ha borrado nada" and the code keeps that promise.
- **One attempt per press.** `retry` returns early unless `statusRef.current === "failed"` and no attempt is running (`use-database-start.ts:49`); the refs make two presses in one render start one attempt; the button is disabled while `retrying`. There is no timer, interval or effect that calls it again: the only automatic call is the mount effect, and `initializeDatabase()` shares the in-flight promise, so StrictMode's double effect opens once.
- **Deep link while the message shows.** `_layout.tsx:56-59` returns `null` while opening and the message while failed, so the `Stack` (and every route) is not rendered: no route code runs and no write can happen. After a successful retry the `Stack` mounts at the linked route, which is the same read-only open as a normal launch (existing audit: routes carry only numeric ids, every write is from a press).
- **Splash and rendering.** `hideAsync()` is called once the status leaves `opening` (`_layout.tsx:52-54`), so the coach no longer sees the splash forever. This closes SEC-D2-3 (silent unusable app). The earlier claim in this file that "`_layout.tsx:26` renders nothing until the database is open" is now `_layout.tsx:56`; the guarantee is the same.

### T088 · blocked permissions

- **`app.config.js` is plain and safe.** 25 lines: it reads only `process.env.APP_VARIANT`, returns `config` untouched unless the value is exactly `"production"` (`!==` strict comparison, so `Production`, `prod` or an empty value do nothing), and then adds `android.permission.INTERNET` once. No network, no file access, no `eval`, no `require` besides the CommonJS export. Semgrep clean.
- **Generated manifest, checked.** Without `APP_VARIANT`: `INTERNET` present (no marker); `SYSTEM_ALERT_WINDOW`, `VIBRATE`, `READ_EXTERNAL_STORAGE` and `WRITE_EXTERNAL_STORAGE` have `tools:node="remove"`. With `APP_VARIANT=production`: the same four plus `INTERNET` have `tools:node="remove"`. `android:allowBackup="false"`, `android:dataExtractionRules="@xml/data_extraction_rules"` and `android:fullBackupContent="@xml/full_backup_content"` are present in both; the XML files have 9 and 18 `domain` entries (nine domains, as the checklist requires). The four permissions are blocked for every profile.
- **Development keeps `INTERNET`.** Correct and necessary: the dev client and the debug build reach Metro through it. The generated `android/app/src/debug/AndroidManifest.xml` (Expo template) also adds `SYSTEM_ALERT_WINDOW` and `usesCleartextTraffic="true"` for debug builds only. Not in the release variant; I did not build one to confirm.
