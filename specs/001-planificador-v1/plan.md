## Explanation before running

- **What:** we build the whole of v1 of the app in three deliveries. **D1** is the "rules engine": the code that knows the regulations (which cells turn light red, which player is in red, when a sixth X is not allowed, what a tap does, what Undo reverts). It has no screens, only functions and tests. **D2** turns it into an app you can use in a match: teams, players, matches, call-up, the grid with undo and overtimes, every warning and its legend, all saved on the device at each tap and kept out of device backups. **D3** adds substitutions and the long-press menu, the match lists, editing and deleting matches, changing the format, and keeping the squad up to date, and then closes the spec.
- **How:**
  1. A documentation-only PR, from branch `001-planificador-v1-spec`, puts the spec, this plan, `tasks.md`, the phase 4 review and ADR-004 on `main`.
  2. **D1** (branch `001-planificador-v1-d1`, T001–T023): first the traceability script learns three-digit global IDs and the glossary gets the new terms, then the rules in `src/domain/`, one file per rule, with the spec examples as test tables, random-data properties and mutation testing.
  3. **D2** (branch `001-planificador-v1-d2`, T024–T061 and T080–T088): the backup exclusion, the database (`src/data/`), the stores and the view model of the open match (`src/state/`), and the screens (`src/app/`, `src/ui/`) for US1–US4, with Maestro journeys on the simulator.
  4. **D3** (branch `001-planificador-v1-d3`, T062–T079 and T093–T100, reviewed on 2026-11-21): US5–US7 in the same layers, and the closing task.
  5. Before D2 and D3 start, this plan is reviewed with what we learned, and you approve it again.
- **Why:**
  - The rules go first and on their own because they are the heart of the app and the hardest part to get right (above all "rule impossible to meet" and Undo after the grid changes shape). With no screens in the way, every example of the spec becomes a test that a machine checks.
  - Three PRs instead of one: each one is small enough for Codex to review well, and after D2 you already have an app you can try in a real match.
  - "Rule impossible to meet" is solved as a flow problem (like water through pipes with minimum and maximum widths) instead of trying every combination: trying them all can mean 2⁷² cases, while the flow answers in microseconds and is exact.
  - The state layer publishes a ready-made "view" of the match (columns, cells, colours, counters, sorted players, legend), so the screens only draw it and never call a rule.
  - The Undo history lives as long as the match screen does. Opening the match's call-up, a new player or its details puts a screen on top of the grid, and the grid stays underneath, so Undo still works when you come back; only going back out of the match removes the grid screen and empties the history (D48). Emptying it whenever the grid is hidden was discarded, because it would break E-026.
  - Creating a match swaps the new-match form for the grid of the match (`router.replace`) instead of putting the grid on top of the form, so Back from the grid goes to the team and never to the filled form, where «Guardar» could create the same match twice (review P-30).
  - Discarded: one branch for the whole spec (too big), one branch per story (seven PRs, and US1–US4 are not usable separately), saving the grid with a "Save" button (it breaks principle 4), a Babel plugin to bundle the migrations (unmaintained since 2018; a small script of our own does the same job).
- **To learn:**
  - **TypeScript:** union types with a `kind` field (a tap returns "changed", "ask sub or starter" or "confirm removal"), `readonly` types, template literal types for keys such as `P3`, type guards, and `import type`.
  - **Tests:** `it.each` tables, fast-check properties and a brute-force oracle, Stryker mutants and coverage, React Native Testing Library, Maestro flows.
  - **Algorithms:** maximum flow with lower and upper bounds, for "rule impossible to meet".
  - **Data:** SQLite tables, foreign keys with cascade delete, transactions, Drizzle schemas and generated migrations.
  - **State:** a Zustand store, actions, a view model, and an undo history.
  - **Expo and React Native:** Expo Router dynamic routes (`[teamId]`) and `useLocalSearchParams`, Stack screens and modals, what happens to a screen when another is pushed on top (it stays mounted) and when it is popped (it unmounts, and the cleanup of its `useEffect` runs), `router.push` versus `router.replace` (adding a screen to the history or swapping the current one), screen tests with `renderRouter` from `expo-router/testing-library`, `Modal` and its `onRequestClose` for the Android Back button, `useWindowDimensions` for phone and tablet in both orientations, horizontal `ScrollView` with a fixed column, long press with react-native-gesture-handler 3, native date and time pickers from `@expo/ui`, and a config plugin that writes native settings (Android backup rules, iOS backup exclusion).
- **To check it:**
  - **D1:** `npm run verify` green, including mutation testing; read `src/domain/spec-examples.test.ts`, where each domain example of the spec is one row of a table.
  - **D2:** on iPhone, iPad and Android, in portrait and landscape: create a team with players, create a match, plan the periods, open the call-up and come back to check that Undo still reverts your last mark, see the warnings and the legend, close the app halfway and reopen it, and press Back from a newly created match to see that you land on the team and not on the new-match form. Maestro journeys green. On the simulator, the database folder carries the "excluded from backup" mark.
  - **D3:** record substitutions, use the long press (and its «Cancelar»), press the Android Back button with a question open, change the format in the match details and leave without «Guardar» to see that the new format stays, edit and delete matches, deactivate players and delete a team; finally, a whole match with airplane mode on.

### Decisions taken while planning

All of them are recorded in the spec; the plan only follows them.

1. **Number order and "07":** sorted by numeric value, "0" before "00", then by name; "07" is not valid (RF-016, RF-042, E-020, E-021).
2. **Input limits:** 40 characters for names and category, 500 for notes, scores 0–999; a field at its limit stops accepting text with no message (RF-013, RF-016, RF-025, E-022).
3. **Date and time:** native pickers of `@expo/ui`, date «01/03/2026», time «18:30», «Quitar hora» (RF-083, E-023, E-032). From 2026-11-18, without a time the field shows «Sin hora» and «Añadir hora» and no picker, and «Añadir hora» gives 12:00 (RF-083, E-033, D51, D52; see "Change of 2026-11-18").
4. **Format in the new-match form:** filled with the team default and changeable without confirmation (RF-084, E-024).
5. **Save failure:** the change is not applied and `error.saveFailed` is shown (RF-085, E-025).
6. **Backups:** the data is kept out of iOS backups and out of Android backup and device-to-device transfer, decided now and configured in D2 (RF-088, E-028; see "Backup exclusion").
7. **Undo after a structural change:** missing cells are skipped; an action with no cell left is discarded and the same press goes on (RF-057, RF-086, E-026, E-031).
8. **Warning marks:** «!» and «≠» in the headers, and a legend of the visible marks (RF-065, RF-066, RF-087, E-027).
9. **Drizzle:** the stable 0.45 line, not the 1.0 release candidate; accepted by Fernando on 2026-11-11.
10. **Confirmations:** only explicit buttons close them; tapping outside and the Android Back button do nothing (RF-015, RF-022, RF-029, RF-034, RF-039, RF-059; D44, D46).
11. **A new match starts with no time** (RF-025: only the format and the date have a default).
12. **Leaving the match:** only going back out of it empties the Undo history; its call-up, new-player and details screens keep it (RF-057, D48; see "Leaving the match").
13. **Tablet with more than 12 players:** every period still fits across and the grid scrolls vertically (RF-081, D49).
14. **Format change in the match details:** saved at once when confirmed, outside «Guardar» (RF-039, RF-082, D50; see "US6").

### Change of 2026-11-18 · Time field without a time (RF-083, E-032, E-033, D51, D52)

- **Level:** Medium ("Change in specs/001"). The spec was updated and clarified on 2026-11-18: RF-083, E-032 and the US2 criterion 6 changed, E-033 added, keys `match.noTime` and `match.addTime` added, D51 and D52 answered. It touches no file in `src/domain/`, `src/data/` or `src/state/`.
- **Branch and tasks:** `fix/match-time-empty-state`, from `main` after D2; T089–T092 in `tasks.md`, section "Change of 2026-11-18".
- **Approval:** Fernando, 2026-11-18 (chat, "Apruebo"), after the phase 4 review in `review.md`.

#### Explanation before running

- **What:** on the iPhone, «Quitar hora» seemed to do nothing. The match had no time, but the time wheel still showed 12:00, because a picker always needs a value and the field gave it noon. Now the time field has two clear states, on iPhone and on Android. Without a time, it shows «Sin hora» and an «Añadir hora» button, and no picker. «Añadir hora» gives the match 12:00 and shows the picker and «Quitar hora». «Quitar hora» goes back to «Sin hora». This applies to the new-match form now, and to the match details when that screen arrives in D3.
- **How:**
  1. **T089 · iOS.** `src/ui/date-time-field.tsx` draws the time part from the draft's `time`. With `null`, it shows the new component `NoTime` (`src/ui/no-time.tsx`: «Sin hora» and the «Añadir hora» button). With a time, it shows the time, the inline picker and «Quitar hora». «Añadir hora» calls the `onTimeChange` the field already has, with `ADDED_TIME` (12:00), a new constant in `src/ui/date-time-field-shared.ts`. `src/i18n/es.json` gets `match.noTime` and `match.addTime`. The iOS tests that expected the old field are updated in the same commit.
  2. **T090 · Android.** `src/ui/date-time-field-android.tsx` gets the same two states with `NoTime`. «Añadir hora» calls `onTimeChange(ADDED_TIME)` and opens the time dialog at once. The dialog's «Cancelar» keeps 12:00. With a time, the «Hora» button shows it and opens the dialog again. The Android tests are updated in the same commit.
  3. **T091 · The whole form.** Screen tests of E-033 and of the form half of E-032 that press the real «Guardar», on both platforms. The US2 Maestro flow (`e2e/us2-match-and-call-up.yaml`) and its static test (`tests/e2e/us2-flow.test.ts`) learn «Añadir hora».
  4. **T092 · Close.** Verification, Codex review, `summary.md` and the PR.
  - **Not touched:** `src/ui/match-form.tsx`, which already passes `setTime` and `clearTime` to the field; `src/state/new-match-draft.ts`, whose `setTime` and `clearTime` already do what is needed; `src/domain/`.
- **Why:**
  - **The data decides whether there is a time.** The field shows «Sin hora» when the draft's `time` is `null` and the picker when it is not. «Añadir hora» writes 12:00 in the draft with the existing `setTime`. So what the screen shows and what «Guardar» saves can never disagree, which is exactly what went wrong on the iPhone. E-033 also asks for the match to have 12:00 right after «Añadir hora» (D51), so the time must be in the data, not only on the screen.
  - **12:00 lives in the interface layer.** It is the value the picker offers, not a rule of the regulations, so it does not go to `src/domain/` (constitution 16). The state layer needs no new action, because `setTime({ hour: 12, minute: 0 })` already stores it. The details screen of D3 (T072) reuses the same field, passing its own time and setters, so it gets the same behaviour.
  - **Android takes 12:00 at once and opens the dialog (D52),** so both platforms follow one rule, and the dialog's «Cancelar» only closes it. The deviation of 2026-11-14 ("only a confirmed selection is committed", so that an untouched 12:00 is never saved) still holds: 12:00 is stored only because the coach pressed «Añadir hora», never because a picker appeared.
  - `toLocalDate` keeps its noon fallback. It now only feeds the date picker, which needs a `Date` (noon keeps the day safe from daylight-saving changes at midnight). The time picker is never drawn without a time.
  - **Discarded:**
    - A local "picker shown" flag in the component (`useState`): the screen could say "there is a time" while the draft has none, the same mismatch as the bug, and E-033 needs 12:00 in the data.
    - A new draft action `addTime()` holding 12:00 in `src/state/`: the default would be split between the draft and the details screen of D3, and `setTime` already does the job.
    - 12:00 in `src/domain/` (for example in `newMatchDefaults`): it is not a regulation rule, and a domain change would also bring mutation testing for nothing.
    - Keeping the «Hora» button on Android without a time, as today: RF-083 asks for «Sin hora» and «Añadir hora» on both platforms.
- **To learn:**
  - **React:** conditional rendering (`time === null ? <NoTime … /> : …`); one source of truth: the component shows what its props say instead of keeping its own copy in `useState` (derived state); a native view that exists only while it is mounted: the inline iOS picker appears only with a time, and the Android dialog is mounted on demand with `useState` and guarded with `useRef`.
  - **TypeScript:** narrowing `string | null` with `=== null`; a `readonly` constant object (`ADDED_TIME`) with the same type as the parameter of `onTimeChange`.
  - **React Native and Expo:** `Platform.OS` choosing the iOS or the Android field; `Pressable` with `accessibilityRole="button"`, which is how the tests find «Añadir hora»; the `@expo/ui` `DateTimePicker` with `presentation="inline"` and `presentation="dialog"`.
  - **Tests:** `queryByRole` of React Native Testing Library returning `null` to prove that something is not there; `jest.replaceProperty(Platform, "OS", "android")` to test the Android field; updating a test because the spec changed, keeping its intent, which is not the same as weakening it.
- **To check it:**
  - `npm run verify` green.
  - **iPhone:** open a new match. Under «Hora» you see «Sin hora» and «Añadir hora», no time wheel and no «Quitar hora». Press «Añadir hora»: «12:00», the wheel on 12:00 and «Quitar hora».   - **Android:** the same start. Press «Añadir hora»: «12:00» and «Quitar hora» appear and the time dialog opens on 12:00. Press «Cancelar»: the dialog closes and «12:00» stays (D52). Press the «Hora» button, which shows «12:00», choose 18:30 and «Aceptar»: «18:30». «Quitar hora»: «Sin hora» and «Añadir hora».
  - Create a match after «Quitar hora»: it is saved with no time. D2 has no match list where you could see it (T071, D3); the Jest tests of T091 check what is saved.

#### Design

- **State:** no change. In the new-match form `onTimeChange` is the draft's `setTime` and `onClearTime` its `clearTime`. In the details screen of D3 they will be that screen's own setters (T072).

  - **Files.** `src/state/`: the session store gets five small slice files (`match-session-commit.ts`, `match-session-pending.ts`, `match-session-questions.ts`, `match-session-menu.ts`, `match-session-format.ts`), plus `matches-store.ts`, `match-details-draft.ts`, `match-fields.ts`, `squad-player-actions.ts` and `squad-team-deletion.ts`. `src/data/`: the match, player and team repositories. `src/ui/`: `choice-dialog.tsx` (question mode), `grid/match-questions.tsx`, `grid/match-header-buttons.tsx` and `grid/match-body-actions.tsx` (taken out of the match screen so that `MatchScreen` stays under 60 lines), `grid/grid-cell.tsx` (long press), `match-list-item.tsx`, `team-sections.tsx`, `match-form.tsx`. `src/app/`: `matches/index.tsx`, `matches/[matchId]/edit.tsx`, `teams/[teamId]/players/[playerId].tsx`, and changes to the team, teams-list, match and layout routes. `src/domain/match-order.ts`. `src/i18n/es.json` (the keys are listed in "D3 design after the review of 2026-11-21"). - **Why:**
  - **One question at a time, in the store.** The question waiting for an answer (`pending`) lives in the session store, not in the screen, so the screen only draws it and every answer goes through the domain again on the current grid. Discarded: a local `useState` in the screen holding the question (the interface would decide what a tap means, constitution 16).

React Native's `Alert` stays discarded (three buttons at most on Android, and it cannot tell a confirmation from a question).

- **Why prune the history.** `pruneHistory` runs right after every change that removes rows or columns (call-up removal, overtime removal, format change), so a column that disappears and later comes back (an overtime removed and added again, or a format changed 8 → 4 → 8) is a new column for Undo, exactly as a re-added player is a new row. `undoLast` also skips missing cells, so both paths give the RF-086 behaviour, and E-026 and E-031 hold.

**"Rule impossible to meet" (RF-067).** The definition asks whether the empty cells of the rule window can be filled with X, keeping every existing X and circled X, so that every window period ends with exactly 5 X and every player in the call-up reaches both minimums.

- For each window period `p`, the X still missing are `d(p) = 5 − X(p)`.
- For each player `i` with `a(i)` X and `e(i)` empty cells in the window, if `k(i)` X are added, they end with `a(i) + k(i)` played and `e(i) − k(i)` rested. Both minimums hold exactly when `L(i) = max(0, minPlayed − a(i)) ≤ k(i) ≤ U(i) = e(i) − minRested`.
- That is a bipartite flow with bounds: source → player `i` with bounds `[L(i), U(i)]`; player `i` → period `p` with capacity 1 when the cell is empty; period `p` → sink with bounds `[d(p), d(p)]`. A filling exists exactly when this network has a feasible flow.
- `bounded-flow.ts` solves it with the standard reduction: subtract the lower bounds, add a super-source and super-sink with the resulting excesses and a return edge sink → source, and run augmenting paths (Edmonds–Karp, breadth-first search). The rule is impossible when the maximum flow does not saturate the super-source. If some `U(i) < L(i)`, it is impossible straight away.
- **Why this algorithm.** It is exact for this definition and its cost does not depend on the number of combinations. The largest case planned (12 players × 6 window periods, and more players if the call-up exceeds 12, RF-010) has at most about 22 nodes, about 100 edges and a total flow of at most 30 (6 periods × 5 X), so the work is a few thousand steps. A search over fillings with pruning was discarded: the number of fillings grows as `C(12,5)⁶ ≈ 10¹⁷` in the worst case, and good pruning is harder to prove correct than the flow. A closed formula (Gale–Ryser style) was discarded because the bounds on both sides and the unavailable cells make it easy to get wrong.
- **How we know it is right (review P-06).** The examples E-003, E-004, E-006, E-007, E-015 and E-030, and a brute-force oracle in `rule-feasibility.oracle.test.ts` that enumerates every filling and must agree with the flow. Small grids would prove nothing (with 5 players or fewer the rule is always impossible), so the oracle uses realistic grids:
  - all three formats, with call-ups from the format minimum to 13 players (4 periods: 8–13; 6 periods: 9–13; 8 periods: 8–13), so that the minimums of 2 are exercised;
  - mostly pre-filled windows: each window period has 5 X minus 0, 1 or 2, with at most 4 X missing in the whole window, plus random circled X in the empty cells, so that brute force only chooses where the few missing X go (a few thousand fillings at most);
  - two generators: a **mixed** one (random players for each X), whose outcomes must include both "possible" and "impossible" (a fixed-seed test asserts at least 20 % of each); and a **possible by construction** one, which starts from a complete valid window (X assigned in cyclic order, which always meets both minimums for in-range call-ups), removes up to 4 X and adds circled X only in cells that were empty in that valid window, so the flow must answer "possible".
- Checked against the spec: E-003 (Juan has 1 empty cell, `U = 1 − 2 < 0`), E-004 (window complete, Pedro needs `L = 1` and no X is missing), E-006 (one X missing for two players with `L = 1`), E-007 (5 X missing, ten players with `U = 1`, feasible), E-015 (8 players give at most 24 of the 25 X) and E-030 (13 players need at least 26 played).

#### Backup exclusion (RF-088, T025 and T026)

- **Checks:** a Jest test (`tests/plugins/with-backup-exclusion.test.ts`) reads `app.json` and the plugin's exported XML and Swift fragments, so the three settings can be checked by reading versioned files (RF-088 criterion). On devices (E-028): on the iOS simulator, `xattr` on the database folder shows the backup-exclusion attribute; on Android, the prebuilt manifest carries both attributes and `adb shell bmgr backupnow` reports that the app does not take part in backup. A test (`tests/scripts/bundle-migrations.test.ts`) fails if `bundle.ts` differs from the SQL files, so a forgotten bundle step turns `verify.sh` red. `src/data/migrations/` is excluded from ESLint and Prettier. `verify.sh` already runs `drizzle-kit check` once `drizzle.config.ts` exists.
- **Opening and migrating:** `src/data/database.ts` opens the database with `openDatabaseSync` from `expo-sqlite`, wraps it with `drizzle()` from `drizzle-orm/expo-sqlite`, and runs `migrate()` with `bundle.ts` once at start-up. - **Every action** follows the data flow of `docs/architecture.md`: ask the domain for the new grid, compute the cell changes (`cellChanges`), write them with `saveCellChanges` in one transaction, then publish the grid, the warnings, the history and the view. If the write throws, nothing is published, the history gets no entry, and `saveFailed` becomes true until the next successful change (RF-085, E-025).
- **Undo (RF-057, RF-086).** Only mark changes push an entry (`undoEntryFor`): taps, menu choices, "remove anyway" and the starter replacement (one entry with its two cells). After a call-up removal, an overtime removal or a format change, the store runs `pruneHistory`. `undo()` calls `undoLast`, saves its `changes` and publishes; if saving fails, the history is kept as it was. `closeMatch()` empties the history and the rest of the session, and after a restart the store starts empty (E-019).
- **Leaving the match (RF-057, D48, review P-21).** `closeMatch()` runs only when the coach leaves the match, which means only that the grid route `/matches/[matchId]` is popped: going back from it to the team screen or to a match list (or, in D3, deleting the match, which also pops it). The route below the grid is always one of those: the grid is pushed from the team screen or a match list, and it replaces the new-match route when a match is created (see "After «Guardar»" under "Interface and navigation"). The match's own routes (`call-up`, `new-player` and, in D3, `edit`) are always opened with `router.push` on top of the grid, never with `replace`, and the native stack keeps the grid screen mounted underneath, so opening them and coming back keeps the session and its history (E-026 through the call-up screen, RF-086 after a format change in the details).
  - **How:** `useOwnSession` closes the session in a `useEffect` cleanup, which React runs only when the screen unmounts, that is, when its route is popped, and only if the session is still this screen's (`view.matchId` equals its id). It opens the match in `useFocusEffect`, but only when the session is not already open for this match, so coming back from a child route keeps the session and its Undo history, and coming back after another match took the store restores this one. Blur events never close anything, because the grid also loses focus when a child route is pushed.
  - **Child routes without the grid below:** they act on the open session, so if it is not open for their `matchId` (for example, a stale link), they show `notFound.message` and change nothing.
  - **Tests:** state tests call the store directly (T052); a screen test with `renderRouter` from `expo-router/testing-library` pushes the call-up route, goes back, and checks that Undo still reverts the last mark, then goes back to the team and opens the match again (straight through its route, since the team's match list arrives in D3) and checks that Undo has nothing to undo (T084); Maestro repeats both on the simulator, reopening the match with a deep link (T056), and E-026 through the call-up screen once the starter replacement exists (T066).

**Grid layout rules.**

- **Fixed player column (RF-077):** a vertical `ScrollView` holds a row with the player column (number, name and the counter «J 3 · D 3» below it) and a horizontal `ScrollView` with the header row and the cells. The header row scrolls with the cells; the player column never scrolls horizontally.
- **Cells ≥ 44 pt (RF-078):** the width is `max(44, ⌊(available width − player column) / period columns⌋)`; when the columns do not fit at 44 pt, the horizontal `ScrollView` scrolls. Rows are at least 44 pt high.
- **375 pt reference (RF-079):** at 375 pt in portrait, 6 periods need 264 pt, which leaves about 100 pt for the player column after margins; long names are cut with an ellipsis. 4 and 6 periods fit; 8 periods and any overtime that does not fit scroll.
- **Landscape phone (RF-080):** 8 periods fit across from 667 pt; more players than fit scroll vertically.
- **Buttons:** «Deshacer», «Añadir prórroga» and «Quitar prórroga» go in the navigation header on tablets and on phones in landscape (window wider than tall), and in a toolbar row under the grid on phones in portrait or square, so that where height is scarce they take no grid height. The call-up button follows the same rule. The warnings sit in a bounded strip that scrolls inside itself on every device: 80 pt on tablets, 60 pt on phones (decided by Fernando, 2026-11-15, Codex sixth run: a landscape phone of 375 pt keeps 375 − 74 − 60 − 44 = 197 pt for the grid, 132 pt at least).
- **What a tablet is (answer of 2026-11-12):** a window whose shortest side is at least `TABLET_MIN_SHORT_SIDE = 768` points (historical: 600 until the decision of 2026-11-14, Codex third run), a constant of `grid-layout.ts` applied to the size from `useWindowDimensions`, so rotation never changes it. Where the buttons go is `buttonsInHeader(width, height)`: tablet or width above height (2026-11-15).
- **Score fields (answer of 2026-11-12):** numeric keyboard and a filter that drops non-digits while typing; the value is stored as a number («007» → 7), so `scoreInvalid` needs no Spanish text (T043).
- **Tablet height (RF-081, review P-19).** 12 rows of 44 pt need 528 pt. Worst case on the 5th-gen iPad in landscape (1024 × 768 pt), with every banner and a full legend at once:

| Item                                                   | Height (pt)   |
| ------------------------------------------------------ | ------------- |
| Status bar                                             | 24            |
| Navigation header, with the grid buttons               | 50            |
| General warning (RF-067), one line at 1024 pt          | 36            |
| Legend (RF-087), four items in a wrapping row, 2 lines | 48            |
| Call-up range banner (RF-068), one line                | 36            |
| Column header row                                      | 44            |
| **Total above the rows**                               | **238**       |
| Left for rows: 768 − 238                               | **530 ≥ 528** |

In portrait (768 × 1024) the banners may wrap to two lines (about 300 pt in total), which leaves about 720 pt. `grid-layout.ts` takes the measured heights of the banners, the legend and the header (from `onLayout`) and returns the row height `max(44, min(56, rows space / rows))` and whether vertical scroll is needed; T053 tests it with this worst case at 1024 × 768 and 768 × 1024, and the device check of T057 confirms it. The 2 pt margin is thin, so it is a risk (see "Risks").

- **More than 12 players on a tablet (RF-081, D49, review P-25):** the width rule does not change, so every period of the format still fits across without horizontal scroll; the rows keep the 44 pt minimum and the rows that do not fit are reached with the vertical `ScrollView` that already holds the grid. T053 tests 13 players at 1024 × 768 and 768 × 1024: 8 periods with no horizontal scroll in both, vertical scroll needed in landscape (13 × 44 = 572 > 530 pt) and not in portrait.

- `useWindowDimensions` recomputes the layout on rotation; `app.json` already has `orientation: "default"` and `supportsTablet: true`.

## Test strategy

- **Order in each task:** the Test designer writes the tests from the task's scenarios, sees them fail for the right reason, and only then the Implementer writes code (AGENTS.md, phase 6).
- **Names:** each test starts with the IDs it covers (`'RF-062 E-001: …'`), so the traceability script can follow them. The script reads only the literal first argument of `it`, `test` and `it.each(…)(…)`: a table is a named constant, and its one literal title carries every RF and E ID of the table; IDs in rows, `%s`, `${}`, `describe` or comments do not count (D1 lesson, D2 rule 2 in `tasks.md`).
- **Focused and skipped tests:** from T085, `scripts/check-focused-tests.sh` flags calls at the start of a line (`it.only(`, `fit(`, `describe.skip(`…, also with a generic) and skipped functions used as values (`? describe : describe.skip`), so words such as "fit" in a title no longer fail `verify.sh`; it exits 2 when a folder it is given does not exist.
- **Size of test files:** from T080, ESLint's 250-line limit also covers `tests/`, `scripts/` and `plugins/`; the four test files above it are split without deleting or weakening any test.
- **Mutation testing in D2:** locally incremental (`STRYKER_INCREMENTAL=1 npm run verify`; `verify.sh` already supports it), full in T030, T037, T061 and when `tests/support/`, `jest*.config.js` or `stryker.config.json` change (`STRYKER_INCREMENTAL=1 STRYKER_FORCE=1 npm run verify`); on CI incremental with the cache key kept as it is.
- **Mutation testing in D3 (review of 2026-11-21):** T062–T066, T093, T094, T097 and T100 do not touch `src/domain/`, so `verify.sh` skips Stryker; T067 is the only D3 task that does (T063, T098 and T099 do not), but from T067 on every run includes Stryker, because it compares the branch with `main`. T067 is the first D3 change there; from then on every local run is incremental (`STRYKER_INCREMENTAL=1 npm run verify`), with full local runs (`STRYKER_INCREMENTAL=1 STRYKER_FORCE=1 npm run verify`) in T067, T098 (it adds `tests/support/session-arbitraries.ts`) and T079 and in any later task that changes `tests/support/`, `tests/setup/`, `jest*.config.js` or `stryker.config.json`. `match-order.ts` ends with no surviving mutant, or each one classified in `review.md`; the 27 survivors classified at the D2 close stay the known list. Stryker runs without `ios/` and `android/` in the working copy (it failed copying `ios/Pods` in D2).
- **Maestro in D3:** D3 rule 8 in `tasks.md` (Release builds on both platforms, the limits found in D2, app problems as findings).
- **Maestro and traceability:** a flow counts as a test of every ID in its non-comment text, so IDs go only in the flow's `name`, and every ID a machine can check also has a Jest test (review D2-A-05).
- **Surviving mutants of `undo.ts` (decision of the D2 review, 2026-11-12).** Documented, not treated with a task. About eight mutants of `src/domain/undo.ts` survive. They are either equivalent (for example, `cellState(current, change.cell) !== "starter"` in `revert` replaced by `true`: the next line skips the change anyway; or the `^` of `/^(P|OT)/` removed, since a column key always starts with `P` or `OT`) or reachable only with a history that does not match the grid: the guards against a sixth X and against re-writing a cell already in its state. Real actions cannot build such a history, because the store runs `pruneHistory` after every call-up removal, overtime removal and format change (T042, T051, D3 T070). The guard stays as a defence against a state bug that forgets to prune, and `undo.five-x.test.ts` already pins its behaviour with mismatched histories. Writing tests only to kill equivalent mutants would test the order of internal steps, not behaviour, and the score (93.89 %) is well above the 80 % threshold. D2 does not change `undo.ts`, so the incremental runs reuse these results. At T061 the Verifier lists them from the HTML report, each classified; any new survivor in `undo.ts` outside that list is a finding.
